# Repository Guidelines

## Project Structure & Module Organization

Ryujinx is a C# Nintendo Switch emulator targeting .NET 10. The solution is
in `Ryujinx.sln`; production projects and shared subsystems live under `src/`
(`Ryujinx`, `Ryujinx.HLE`, `Ryujinx.Cpu`, graphics, audio, input, and Horizon
modules). NUnit tests are in `src/Ryujinx.Tests`, `src/Ryujinx.Tests.Memory`,
and `src/Ryujinx.Tests.Unicorn`. Developer documentation is in `docs/`,
packaging and legal assets are in `distribution/`, and helper scripts are in
`scripts/`.

## Build, Test, and Development Commands

- `nix develop` enters the pinned shell with the .NET SDK and Linux runtime
  libraries. Use `nix develop path:.` when testing an uncommitted flake.
- `dotnet restore Ryujinx.sln` restores centrally managed NuGet dependencies.
- `dotnet build Ryujinx.sln -c Release -o build` builds the full release output.
- `dotnet test Ryujinx.sln -c Release` runs the NUnit test projects.
- `dotnet format` checks and applies repository formatting; review the diff
  before committing.
- `./scripts/run-debug.sh` launches the GUI through the Nix shell and is useful
  for Linux development. Pass emulator arguments after the script name.

## Coding Style & Naming Conventions

Follow `docs/coding-guidelines/coding-style.md` and the existing file style.
Use four spaces, Allman braces, explicit visibility, PascalCase for public
types and methods, `_camelCase` for private instance fields, and `s_` for
static fields. Keep `using` directives outside namespaces, prefer language
keywords (`int`, `string`), and run `dotnet format` before review. Keep
generated files under their existing `Autogenerated/` directories; do not edit
them manually unless the generator workflow requires it.

## Testing Guidelines

Add NUnit tests beside the relevant subsystem, using descriptive names ending
in `Tests` (for example, `TreeDictionaryTests.cs`). Run the focused project
while iterating, then run `dotnet test Ryujinx.sln -c Release` before opening a
PR. Investigate failures rather than weakening or skipping tests.

## Commit & Pull Request Guidelines

Use concise imperative commit subjects (the project recommends 50 characters
or fewer), with wrapped detail at 72 columns and `Fix #123` when applicable.
Keep commits and PRs focused; link the issue, explain behavior and validation,
and include screenshots or logs for UI or platform-specific changes. PRs must
build cleanly, pass tests and formatting checks, and address review feedback
in follow-up commits. Avoid unrelated style-only changes and unreviewed
dependency or licensing changes.
